# **CoChem-CORE: The Master Environment & Registry Orchestrator**

## **Overview**

**CoChem-CORE** is the absolute foundation of the CoChem Pipeline. It is not a computational chemistry engine itself; rather, it is the strict, deterministic environment provisioner (Stage 0).

In modern computational chemistry, dependency conflicts between ML potentials (like MACE/PyTorch) and legacy electronic structure tools often cause catastrophic pipeline failures. CoChem-CORE solves this by building isolated **micro-silos** for each dependency group and generating a cryptographically hashed state matrix (cochem\_system\_config.json). This JSON file acts as the authoritative truth for all downstream hardware, memory, and engine routing.

## **Architecture: Frontend vs. Backend (Separation of Concerns)**

To guarantee execution stability, the CoChem ecosystem strictly separates the graphical interface from the OS-level environment setup.

* **The Frontend (CoChem-UNITY / CoChem-DOCK):** You do not need to build your pipeline via the terminal. CoChem-UNITY provides a visual, browser-based master dashboard where you select which repositories to install, triage molecules in 3D, and configure your parameters. It outputs your selections into a cochem\_deployment\_manifest.json.  
* **The Backend (CoChem-CORE):** This repository is the headless, terminal-based engine. It reads the manifest generated by UNITY and executes the heavy OS-level commands (creating Conda silos, downloading binaries, compiling OpenMPI).  
* **The Bridge:** Once CORE finishes building the environments, it generates cochem\_system\_config.json. The UNITY GUI actively polls for this file; once detected, the GUI unlocks the rest of the pipeline tabs.

## **Scientific & Technical Trade-offs**

* **Micro-Silos vs. Monolithic Environments:** We trade slightly higher disk usage (multiple Conda/venv silos) for absolute execution stability. PyTorch will never conflict with RDKit or ORCA bindings because they are sandboxed and invoked via subprocess routing.  
* **Dynamic Hardware Routing:** Rather than hardcoding memory limits in input files, CORE assesses your system's VRAM, RAM, and CPU threads at runtime. It enforces a strict 10% memory reserve for the Linux kernel and Jupyter daemon, mathematically preventing out-of-memory (OOM) hard crashes during heavy Coupled Cluster (CCSD(T)) runs.

## **Installation & Setup**

Installation is simply cloning the repository into your working directory (or launching the associated Codespace/DevContainer).

git clone \[https://github.com/CoChem/CoChem-CORE.git\](https://github.com/CoChem/CoChem-CORE.git)  
cd CoChem-CORE

## **How to Run (The Stage 0 Standard)**

**Option A: The GUI Route (Recommended)**

Simply launch CoChem-UNITY. The UI will guide you through your module selection and automatically invoke the CoChem-CORE scripts in the background via subprocesses.

**Option B: The Manual / HPC Route**

If you are operating on a headless cluster without UI access, CoChem-CORE must be executed in a strict five-phase sequence. If using a Jupyter Notebook, execute these sequentially:

1. **System Discovery:** Scans OS, permissions, and available paths.  
   \!python cochem\_setup\_1\_sys.py  
2. **Hardware Telemetry:** Maps CPU topologies, RAM, and GPU VRAM.  
   \!python cochem\_setup\_2\_hw.py  
3. **Engine Verification:** Locates ORCA 6.1.1, PySCF, and xTB binaries. Performs hash-masking for sudo-restricted binaries.  
   \!python cochem\_setup\_3\_engines.py  
4. **Micro-Silo Provisioning:** Builds the isolated Python environments required for downstream tasks.  
   \!python cochem\_setup\_4\_silos.py  
5. **Finalization & Registry Generation:** Compiles findings into cochem\_system\_config.json.  
   \!python cochem\_setup\_5\_finalize.py

*Note for HPC Users:* If your ORCA installation is behind a module load system, ensure module load orca/6.1.1 is in your .bashrc before running Phase 3\.

## **Graceful Failure Handling**

If setup fails, the scripts will not crash your Jupyter kernel or GUI. It will output an explicit error (e.g., PermissionError for binary paths) and log the failure. Check logs/setup\_trace.log to identify the broken phase. You can safely re-run the failed stage after correcting the path/permission issue.
